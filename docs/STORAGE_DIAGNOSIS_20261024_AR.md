# تشخيص توقف حسابات المدرسة عند التخزين

الفحص المباشر بتاريخ 24 أكتوبر 2026 أعاد من المدرسة: `data_core_storage_unavailable`, `reason=ENOENT`, `stage=storage`. الريلز يعمل بالإصدار `3.7.1-viewer-stability`. السجل المقدم يعود إلى 21 أكتوبر ويعرض مساراً قديماً؛ لا يكفي لتحديد عملية الملفات التي تفشل الآن.

إذا لم يضبط `APP360_DB_FILE` أو `APP360_UPLOAD_ROOT`، تبقى المسارات الافتراضية كما كانت: `services/app360-data-core/var/app360.sqlite3` و`services/app360-data-core/var/uploads` نسبة إلى جذر المدرسة. لا ينشئ هذا التحديث قاعدة بديلة ولا يغير المسار أو المفتاح. يميز التشخيص الجديد بين database_directory وdatabase_file وuploads_directory، وبين mkdir وstat وwrite وunlink، دون كشف المسارات عبر واجهة الصحة العامة.

## فحص الاستضافة دون طرفية

بعد تحديث المدرسة من main، استخدم Node 22 LTS حديثاً، وأبقِ Build Command كما هو:

```sh
npm run build
```

تبيّن من سجل SmarterASP أن الأمر المركب باستخدام && يمنع اكتشاف ملف تشغيل Node رغم نجاح البناء. استخدم في Start Command ملف التشغيل المباشر:

```sh
node services/family-relay/src/server.js
```

أضف مؤقتاً APP360_STORAGE_DIAGNOSTICS=1 إلى Environment Variables. يطبع التطبيق الفحص عند بدء التشغيل نفسه. الفحص للقراءة فقط: لا يفتح SQLite ولا ينشئ مجلدات ولا يقرأ قيمة المفتاح. يطبع المسارين الفعليين وحالة كل جزء منهما وما إذا كان رابطاً رمزياً، ثم يبدأ التطبيق المعتاد. بعد جمع التقرير احذف APP360_STORAGE_DIAGNOSTICS أو اجعله 0، وأبقِ أمر التشغيل المباشر. أرسل كتلة السجل التي تبدأ بـ `school-storage-read-only` مع سطر `[APP360_DATA_CORE]` الحديث، ولا ترسل أسرار البيئة. قراءة قابلية الكتابة عبر access ليست بديلاً لاختبار الكتابة الفعلي أثناء تشغيل الخدمة.

ثُبت engines.node في جذر المشروع على 22.x لأن Railpack اختار Node 20 من القيمة السابقة >=20، مستقلاً عن اختيار الإصدار في لوحة الاستضافة. أبقِ اختيار تشغيل الاستضافة Node 22 LTS حديثاً أيضاً.

أضف إلى Environment Variables إذا لم يكن موجوداً:

```dotenv
APP360_PUBLIC_ORIGIN=https://school.yem1.com
```

إذا كان الفشل ENOENT أثناء mkdir رغم الإنشاء المتداخل، فالتقرير يحدد إن كان هناك رابط مكسور، أو مجلد خدمة غير ظاهر للعملية، أو مسار غير موجود في بيئة التشغيل. يجب إصلاح المسار/التركيب أو صلاحيات الاستضافة بناء على التقرير. لا يمكن الجزم بأن تغيير مسار قاعدة البيانات أو إنشاء var في مكان آخر سيصلح المشكلة.

## الحفاظ على البيانات

عند الحاجة إلى نقل التخزين إلى مجلد دائم تتيحه الاستضافة، يجب تحديد قاعدة المدرسة الحالية أولاً وإيقاف الخدمة وأخذ نسخة احتياطية متسقة، ثم ضبط APP360_DB_FILE وAPP360_UPLOAD_ROOT إلى المسارات المؤكدة. لا تضبط مساراً تخمينياً ولا تحذف قاعدة المدرسة أو الريلز. لا تستخدم /tmp أو قاعدة in-memory لتجاوز الخطأ.

## الدخول والتشجيع

نجاح فحص التخزين يسبق تشغيل الترحيلات والتحقق من الربط. يجب أن تعيد `/api/app360/health` حالة 200 و`ok:true` قبل إعادة تجربة رابط دخول جديد. يبقى مصدر هوية الطفل واشتراكه هو الريلز؛ لا يكفي اسم مخزن في المتصفح. تستخدم المدرسة الاسم الرسمي فقط بعد تأكيد الجلسة وحق named_encouragement، وتتوقف التسمية عند انتهاء الاشتراك/الجلسة. الاختبارات المعزولة نجحت؛ لا يعد ذلك تأكيداً لنجاح حساب نور على الاستضافة قبل إصلاح التخزين وتجربة الدخول الفعلي.
