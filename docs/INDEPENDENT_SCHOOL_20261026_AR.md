# فصل مدرسة العائلة — 26 أكتوبر 2026

## المسؤوليات والهوية

الريلز هو المصدر الوحيد لحساب ولي الأمر والطفل والمتدرب، وكلمات المرور وPIN والاشتراك والتجديد. المدرسة تحتفظ بإسقاط للمعرف الرسمي من أجل علاقات البيانات، دون إنشاء كلمة مرور أو PIN ثانٍ. جداول المدرسة وتقاريرها ووسائطها وإعداداتها في قاعدة المدرسة وحدها. لا تصدر المدرسة إحصاءات التطبيقات إلى الريلز. تستمر نبضات التحقق من الاشتراك والوقت المسموح ضمن سلطة الاستحقاق في الريلز؛ لا تحمل تقارير التطبيقات التفصيلية.

من إدارة الريلز يُفتح «إدارة محتوى المدرسة» برمز استخدام واحد، ومن لوحة المدرسة زر «إدارة محتوى الريلز» يعود بجلسة للحساب الرسمي نفسه. الرموز قصيرة العمر، ومفتاح الربط يبقى بين الخادمين. لا يُستنتج إذن ولي الأمر أو المدير العام من دور يرسله المتصفح. تُحدّث قائمة الأبناء من الريلز وتُعزل صلاحيات المسؤول الفرعي عن بقية أبناء الأسرة. حذف الصلاحية أو انتهاء الجلسة الأصلية يمنع استعمال الرابط القديم.

## النشر والفصل الآمن

1. احتفظ بنسخة احتياطية كاملة من قاعدتي الريلز والمدرسة وإعداداتهما الخاصة، واختبر استعادتها.
2. ارفع باتش الريلز 4.0.0 أولاً وأعد تشغيله، ثم انشر هذا الإصدار من المدرسة. لا تصفّر أي قاعدة ولا تغيّر مفتاح الربط.
3. تدخل المدرسة من حساب المدير العام الرسمي، ثم تفتح dashboard.html وتنفذ «نقل البيانات والتحقق والفصل» مرة واحدة. يحتاج الأمر جلسة مدير عام صالحة ومفتاح الربط معاً.
4. تنقل المدرسة سجل الإضافة والإعدادات وسياسات الأسر واستثناءات التطبيقات والاستخدام اليومي وإيصالات الاستلام إلى أرشيف نقل داخلي بصفحات 500 سجل. تتحقق من العدد وSHA-256 لكل جدول ومن حفظ السجلات، ثم تعيد الإقرار للريلز. يعيد الريلز حساب البصمات تحت قفل كتابة في معاملة قبل حذف الجداول الأربعة القديمة وسجل إضافة المدرسة فقط. إذا اختلف المصدر يتوقف الحذف ويُعاد النقل بلقطة جديدة. لا تُحذف الحسابات أو الاشتراكات أو جداول الريلز.
5. أصبحت جداول الربط التقنية في الريلز identity_bridge_grants/codes/auth_limits؛ migration يعيد تسميتها مع الاحتفاظ بالجلسات. identity_bridge_handoffs يحفظ بصمات وتدقيق النقل فقط. لا يجري حذف جداول الأعمال عند تشغيل الخادم.
6. تحقق من إعدادات الأسر، والتقارير السابقة، ودخول الأب والطفل في الاتجاهين قبل اعتبار القطع مكتملاً. لا تستبدل قاعدة المدرسة بقاعدة فارغة بعد اكتمال النقل؛ استعد نسخة المدرسة المطابقة إذا لزم.

البيانات المنقولة المتداخلة مع إحصاءات المدرسة تُدمج بالأكبر لكل طفل/تطبيق/يوم، دون عدّ مزدوج. تظل السجلات الأصلية في أرشيف النقل. إذا كان الاستعمال في النظامين مستقلاً قبل الفصل، لا يمكن استنتاج زمن اتحادهما بدقة من المجاميع اليومية وحدها.

## صوت ولي الأمر والفيديو

لوحة المدرسة توفر صوتاً مستقلاً لكل طفل حتى 15 ثانية و2 MB، ومعاينة واستبدالاً وحذفاً. يُشغل عند وجود اشتراك فعّال يسمح بالتشجيع الشخصي. عند الانتهاء أو تعذر التشغيل يُستخدم التشجيع العام/المكتبة الرسمية وفق الاستحقاق. لم تتغير مكتبة 2084 ملفاً أو تسجيل نور المعتمد، ولا يُستخدم نطق الجهاز للأسماء.

فيديو البداية حتى 30 ثانية و6 MB؛ التسجيل والمعالجة المحلية يتوقفان عند 29 ثانية. يحاول المتصفح معالجة الملف محلياً بدقة 640×360 و15 إطاراً/ثانية. إذا لم يدعم الجهاز التسجيل/الترميز لا ندّعي نجاح الضغط: يمكن استخدام ملف MP4 قصير بالحجم المقبول أو جهاز أحدث. يتحقق الخادم من الصيغة وحدود الحجم والمدة. متصفحات معينة تمنع التشغيل بصوت تلقائي؛ يظهر زر التشغيل الأصلي عند الحاجة.

فيديو واحد حالي لكل ولي أمر/فريق؛ تحديد طفل أو عدة أطفال من الحساب المسموح، وترك الاختيار فارغاً يعني جميع أبنائه المتاحين في الحساب المختار. يمكن اختيار تطبيق واحد مناسب للفئة يفتح بعد اكتمال الفيديو. يستبدل الحفظ ملف الفيديو السابق ويحذف بايتاته وعلاقاته الحالية، بينما تبقى إحصاءات النسخ السابقة وسجل المهمة. الوسائط خاصة داخل قاعدة المدرسة (bytea في PostgreSQL)، وليست روابط عامة أو ملفات في GitHub. المعاينة الإدارية لا تزيد عداد الطفل.

تُحفظ مرات بدء التشغيل والإكمال لكل طفل ونسخة، وموضع الفيديو غير المكتمل. المهمة تتذكر حالتها ونقطة الاستكمال إن أرسلها التطبيق عبر API، وزر «أنهيت المهمة» إقرار يدوي واضح. ليس هذا تقييماً آلياً للإتقان أو خطة متعددة الخطوات. لا يضمن النظام استعادة كل حالة داخلية لكل لعبة؛ حالة اللعبة الحالية وآلية حفظها تبقيان مسؤولية التطبيق حتى إضافة عقد التكامل المفصل لاحقاً.

## التقارير والبريد

تقارير المدرسة تعرض بياناتها فقط، مع CSV وطباعة، وتفضيل يومي/أسبوعي/شهري/متوقف لكل طفل. تبقى دورية تقارير الريلز مستقلة. تفحص المدرسة البريد الرسمي وملكية الطفل عبر خدمة هوية الريلز قبل الإرسال، ولا تقبل عنوان مستلم من المتصفح. SMTP مستقل اختياري؛ لا يلزم لتسجيل الدخول أو الوسائط. الإرسال عبر outbox مع إعادة محاولة ومنع تكرار منطقي للفترة، لكنه لا يعد بوصول مرة واحدة تماماً إذا انقطع الاتصال بعد قبول مزود البريد الرسالة.

أضف القيم الحقيقية في إعدادات الاستضافة فقط، ولا تضعها في Git:

```dotenv
# اترك إعدادات PostgreSQL الحالية والمفتاح دون تغيير.
# APP360_DB_CLIENT=postgresql
# APP360_FILE_STORAGE=database
# تقارير المدرسة فقط، بعد توفير بيانات البريد:
APP360_EMAIL_REPORTS_ENABLED=0
# APP360_SMTP_HOST=mail.example.com
# APP360_SMTP_PORT=587
# APP360_SMTP_SECURE=0
# APP360_SMTP_FROM=school@example.com
# APP360_SMTP_USER=school@example.com
# APP360_SMTP_PASSWORD=ضعها_في_بيئة_الاستضافة_فقط
```

لا يحتاج PostgreSQL/وسائط قاعدة البيانات APP360_DB_FILE أو APP360_UPLOAD_ROOT. تبقى إعدادات SQLite اختيارية لمحرك SQLite وحده. تثبيت المدرسة: أمر البناء `npm run build` وأمر التشغيل `node services/family-relay/src/server.js` من جذر المستودع؛ لا تضع سلسلة أوامر تشخيصية في Start Command. يحضر البناء اعتماديات خدمة البيانات حسب المحرك. نفذ migrations/seeds من bootstrap النظام المعتاد؛ common ثم مجلد المحرك المحدد. seeds تعيد كتالوج التطبيقات وإعدادات النظام فقط، ولا تعيد إنتاج الأطفال أو تسجيلات الآباء الخاصة من نسخة فارغة.

## الخطوات اللاحقة

قبل إدارة جميع محتويات التطبيقات من اللوحة: حصر مخططات كل تطبيق وعقود نسخها، تعريف صلاحيات ناشر/مراجع/ولي أمر، فصل المسودة عن الإصدار المنشور، تخزين الوسائط والإصدارات مع إجراءات استرجاع، ثم توحيد API لتحميل المحتوى والتحقق منه وحزم offline. لكل وحدة migrations/seeds مستقلة ومعرف ثابت، واختبارات عزل وصلاحيات وترقية متكررة. تبدأ خطة التنفيذ متعددة الخطوات بعقد task_steps ونسخة ثابتة للخطة وسجل إكمال لكل طفل؛ لا تُغيّر خطة الطفل الجارية بمجرد نشر خطة جديدة. تُعتمد كل مرحلة بعد اختبارها قبل نقل التطبيق التالي.

## التحقق وحدوده

71 اختباراً للمدرسة، وفحص ES5 للمسارات المشتركة، وتحديث 18 حزمة offline. تجربة Edge بكاميرا وميكروفون وهميين: تسجيل صوت وفيديو ومعاينتهما وحفظهما وتشغيلهما للطفل وفتح المهمة وإقرار إكمالها، بعرضي 390 و1200. اختبار PostgreSQL محلي مستقل: 14 migration و18 تطبيقاً، لا مستخدمين تجريبيين في production، إعادة تهيئة دون تكرار، نقل وتحقق ومنع الحذف مع كتابة متزامنة، وحفظ bytea واستبدال الوسائط مع بقاء التاريخ. لا تعني هذه الفحوص اختبار Android قديم فعلياً أو النشر في SmarterASP أو إيصال بريد حقيقي. يجب تنفيذ قبول هذه الحالات بعد النشر.
