# معمارية مختبر التطبيق 360 — طويلة المدى

## الفكرة المركزية

نبني **Monorepo واحدًا** يمكنه احتواء عشرات أو مئات التطبيقات التعليمية من مستويات مختلفة، من تطبيق HTML خفيف جدًا لطفل على جهاز قديم، إلى تطبيق حديث بواجهة غنية وخدمات Node.js وAI. القوة ليست في إجبار الجميع على Stack واحد، بل في **توحيد العقود والمصادر والخدمات المشتركة مع السماح لكل تطبيق باختيار العمق الذي يحتاجه فقط**.

## طبقات النظام

```text
┌──────────────────────────────────────────────────────────────┐
│ Platform Shell / PWA                                         │
│ index.html · manifest · sw · ages/* · catalog · goals       │
└──────────────────────────────────────────────────────────────┘
                          ↓ discovers
┌──────────────────────────────────────────────────────────────┐
│ Apps                                                         │
│ apps/<age>/<slug>/                                           │
│ كل تطبيق مستقل في الممارسة والإصدار والتثبيت والتوافق        │
└──────────────────────────────────────────────────────────────┘
                ↓ imports                 ↓ calls
┌─────────────────────────────┐   ┌────────────────────────────┐
│ Shared Packages             │   │ Shared Services            │
│ packages/*                  │   │ services/*                 │
│ كود محلي قابل لإعادة الاستخدام│   │ Node/API/AI/Media/Sync     │
└─────────────────────────────┘   └────────────────────────────┘
                ↓                      ↓
┌──────────────────────────────────────────────────────────────┐
│ Resources & Capability Contracts                             │
│ data/capabilities.json · bundles/* · resources/*             │
└──────────────────────────────────────────────────────────────┘
```

## اتجاه الاعتماد المسموح

```text
Platform Shell ──> catalog/goals
Apps ────────────> packages
Apps ────────────> services عبر API
Services ────────> packages
Packages ────────> packages أدنى مستوى فقط
```

الممنوع:

```text
App A ─X─> ملفات داخل App B
Package ─X─> App
Service ─X─> ملفات واجهة App مباشرة
Age Page ─X─> منطق داخلي لتطبيق فردي
Legacy Route ─X─> نسخة ثانية من التطبيق
```

إذا احتاج تطبيقان الكود نفسه، لا تجعل أحدهما يعتمد على الآخر؛ **استخرج الجزء المشترك إلى Package**.

## أربع مناطق ملكية واضحة

### 1. `apps/`

كل ما يخص تجربة تطبيق واحد: UI، منطق ممارسة، بيانات خاصة، أصوات خاصة، Service Worker خاص، Manifest، Icon، اختبارات، README و`app.json`.

المسار الرسمي الوحيد هو:

```text
apps/<age>/<slug>/
```

لا ننشئ Alias أو Compatibility Gateway موازياً لنفس التطبيق.

### 2. `packages/`

كود reusable حقيقي. قاعدة الاستخراج: مستهلكان حقيقيان أو عقد منصة ثابت. لا ننشئ مكتبة عامة ضخمة مسبقًا.

### 3. `services/`

عمليات تحتاج Server: Secrets، AI providers، معالجة وسائط، مزامنة حالة، مهام ثقيلة، API مركزي. الخدمات Workspaces مستقلة لكن Dependencies مركزيًا عبر pnpm.

### 4. `resources/`

أصول مشتركة قابلة لإعادة الاستخدام: حزم صوت، صور، بيانات تعليمية عامة، قوالب. كل Pack له Manifest يوضح الملكية، الترخيص، اللغة، الإصدار، والاستخدام.

## تطبيق الرسم والكتابة الآن

المصدر الرسمي الوحيد:

```text
apps/1-4/drawing-writing-foundations/
```

كل الصوت والـPCM والمزامنة والـPWA الخاصة به تعيش داخل Boundary التطبيق ما دامت لا تملك مستهلكًا ثانيًا حقيقيًا.

## لماذا لم ننقل كل صوت الرسم إلى مكتبة مشتركة فورًا؟

لأن إعادة الاستخدام يجب أن تكون **مقاسة وليست متخيلة**. عندما يحتاج تطبيق ثانٍ جزءًا من الصوت أو Runtime:

1. نحدد الجزء المشترك فقط.
2. نستخرج Runtime إلى `packages/` إن كان كودًا.
3. ننقل الأصول المشتركة إلى `resources/`.
4. نضيف Adapter داخل المستهلكين إذا احتاجوا اختلافات توافق.
5. نختبر الأجهزة القديمة والحديثة قبل إلغاء الملكية المحلية السابقة.

## PWA كعقد منصة

البوابة الرئيسية PWA مستقلة، وكل تطبيق مستقل يمكن تثبيته منفردًا.

- Root SW يتحكم في البوابة وصفحات الفئات فقط.
- App SW داخل `apps/<age>/<slug>/` يتحكم في تطبيقه فقط.
- لا يتشارك تطبيقان Service Worker scope.
- كل تطبيق له `icon.svg` وManifest وهوية تثبيت مستقلة.
- التطبيقات البسيطة تبدأ `offline-first`.
- التطبيقات التي تحتاج Backend تبدأ `offline-partial` ما لم يكن الاتصال شرطًا جوهريًا للممارسة.

سياسة التفاصيل في `docs/PWA_OFFLINE_POLICY_AR.md`.

## مستويات عمق التطبيقات

- `lite`: HTML/JS محلي، ممارسة واحدة واضحة، صفر خدمات.
- `standard`: PWA، حفظ محلي، صوت/وسائط أو أكثر من مستوى تدريب.
- `advanced`: مزامنة أو تقييم أو تسجيل وسائط أو قدرات متعددة.
- `expert`: خدمات Server، AI، حسابات أو مزامنة متعددة الأجهزة، Processing مركزي.

العمق **ليس تقييم جودة**؛ التطبيق الخفيف قد يكون الأفضل تربويًا إذا كانت المهمة بسيطة.

## Runtime Profiles

- `static-web`
- `legacy-web`
- `pwa`
- `node-service`
- `hybrid-web-service`

يمكن أن يبدأ التطبيق `static-web` ثم ينتقل لاحقًا دون تغيير هويته أو goal keys.

## Capability Model

بدل أن يسأل كل تطبيق: أي مكتبات أركب؟ يعلن **ماذا يحتاج**:

```json
{
  "capabilities": ["storage.local", "audio.recorded", "pwa.offline"],
  "bundles": ["legacy-child"]
}
```

`data/capabilities.json` يصف القدرات، و`bundles/` يجمعها في وصفات شائعة. لاحقًا يستطيع Build Resolver قراءة هذه الحقول وتجميع Dependencies/Services المطلوبة فقط.

## Bundles وليست Mega Framework

- `static-core`
- `legacy-child`
- `collaborative`
- `ai-assisted`
- `full-learning`

لا يعني اختيار Bundle أن كل كودها يحمّل في كل صفحة. هي **Dependency Resolution Input** للبناء والنشر.

## سياسة Node.js والاعتمادات

الجذر يملك:

- `package.json`
- `pnpm-workspace.yaml`
- `.npmrc`
- `pnpm-lock.yaml`

أي تطبيق Node أو خدمة Node لا تنشئ Dependency Universe مستقلًا. تستخدم Workspace الجذر. pnpm يقلل الهدر عبر content-addressed store والربط بين Workspaces، مع `node-linker=hoisted` عندما تحتاج الأدوات توافقًا تقليديًا.

المبدأ ليس «نسخة واحدة بالقوة لكل Dependency»؛ الصحيح هو **إدارة مركزية + dedupe عندما يسمح SemVer + اختلاف مقصود عند الضرورة**.

## التوافق القديم والحديث معًا

لا نجعل Big TAB HD يحدد Stack المنصة كلها:

- Platform Shell يبقى خفيفًا.
- التطبيقات التي تحتاج Legacy تعلن `runtime_profile: legacy-web`.
- التوافق القديم يعزل داخل التطبيق أو Package محددة.
- التطبيقات الحديثة تستطيع استخدام Build حديث دون تحميل Polyfills غير لازمة للجميع.

## Local-first افتراضيًا

عند عدم الحاجة إلى Server:

- البيانات تبقى محليًا.
- لا نرسل أسماء/رسومات/صوت لخدمة خارجية بلا حاجة.
- Progress Sync يضاف كCapability عند وجود سبب حقيقي.
- AI يمر عبر Service/Gateway ولا توضع API keys في المتصفح.
- PWA Cache يخزن ما يلزم للممارسة لا المستودع كله.

## استراتيجية التطوير من محادثات مستقلة

كل محادثة تطبيق تعمل داخل:

```text
apps/<age>/<slug>/
```

وتقرأ العقود العامة فقط. لا تحتاج معرفة تفاصيل تطبيقات أخرى. عند الحاجة إلى شيء مشترك لا تنسخه؛ تسجل أو تنفذ Extraction واضحًا.

## Definition of Done معمارياً

أي تطبيق يصبح `live` عندما:

1. له `app.json` و`package.json` وREADME.
2. رابط الدخول الرسمي تحت `apps/<age>/<slug>/` يعمل مباشرة.
3. goal keys سليمة أو مبرر `modern_extension` واضح.
4. Runtime profile وDepth محددان.
5. القدرات/Bundles المعلنة صحيحة.
6. لا يعتمد على ملفات تطبيق آخر.
7. له Manifest وIcon وSW عندما يكون تطبيق متصفح قابلًا للتثبيت.
8. Offline level واختبار التحديث موثقان.
9. fallbacks الحرجة مختبرة.
10. `node tooling/validate-platform.js` ينجح.

## قاعدة التطور الطويل

لا نعيد بناء المنصة كلها عند ظهور تقنية جديدة. نضيف Package أو Service أو Bundle، وننقل التطبيقات إليها تدريجيًا. الهوية، الأهداف، والمسار الرسمي تبقى مستقرة؛ التنفيذ الداخلي يمكن أن يتطور باستمرار.
