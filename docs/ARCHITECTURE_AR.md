# معمارية مختبر التطبيق 360 — طويلة المدى

## الفكرة المركزية

نبني **Monorepo واحدًا** يمكنه احتواء عشرات أو مئات التطبيقات التعليمية من مستويات مختلفة، من تطبيق HTML خفيف جدًا لطفل على جهاز قديم، إلى تطبيق حديث بواجهة غنية وخدمات Node.js وAI. القوة هنا ليست في إجبار الجميع على Stack واحد، بل في **توحيد العقود والمصادر والخدمات المشتركة مع السماح لكل تطبيق باختيار العمق الذي يحتاجه فقط**.

## طبقات النظام

```text
┌──────────────────────────────────────────────────────────────┐
│ Platform Shell                                               │
│ index.html · ages/* · data/catalog.json · data/goals.json   │
└──────────────────────────────────────────────────────────────┘
                          ↓ discovers
┌──────────────────────────────────────────────────────────────┐
│ Apps                                                         │
│ apps/<age>/<slug>/                                           │
│ كل تطبيق مستقل في الممارسة والإصدار والتوافق                 │
└──────────────────────────────────────────────────────────────┘
                ↓ imports                 ↓ calls
┌─────────────────────────────┐   ┌────────────────────────────┐
│ Shared Packages             │   │ Shared Services            │
│ packages/*                  │   │ services/*                 │
│ كود محلي قابل لإعادة الاستخدام│   │ Node/API/AI/Media/Sync     │
└─────────────────────────────┘   └────────────────────────────┘
                ↓                      ↓
┌──────────────────────────────────────────────────────────────┐
│ Resources & Capability Contracts                             │
│ data/capabilities.json · bundles/* · resources/*             │
└──────────────────────────────────────────────────────────────┘
```

## اتجاه الاعتماد المسموح

الاتجاه قاعدة معمارية، لا مجرد اقتراح:

```text
Platform Shell ──> catalog/goals
Apps ────────────> packages
Apps ────────────> services عبر API
Services ────────> packages
Packages ────────> packages أدنى مستوى فقط
```

الممنوع:

```text
App A ─X─> ملفات داخل App B
Package ─X─> App
Service ─X─> ملفات واجهة App مباشرة
Age Page ─X─> منطق داخلي لتطبيق فردي
```

إذا احتاج تطبيقان الكود نفسه، لا تجعل أحدهما يعتمد على الآخر؛ **استخرج الجزء المشترك إلى Package**.

## أربع مناطق ملكية واضحة

### 1. `apps/`

كل ما يخص تجربة تطبيق واحد: UI، منطق ممارسة، بيانات خاصة، أصوات خاصة، Service Worker خاص، اختبارات خاصة، README و`app.json`.

### 2. `packages/`

كود reusable حقيقي. قاعدة الاستخراج: مستهلكان حقيقيان أو عقد منصة ثابت. لا ننشئ مكتبة عامة ضخمة مسبقًا.

### 3. `services/`

عمليات تحتاج Server: Secrets، AI providers، معالجة وسائط، مزامنة حالة، مهام ثقيلة، API مركزي. الخدمات Workspaces مستقلة لكن Dependencies مركزيًا عبر pnpm.

### 4. `resources/`

أصول مشتركة قابلة لإعادة الاستخدام: حزم صوت، صور، بيانات تعليمية عامة، قوالب. كل Pack له Manifest يوضح الملكية، الترخيص، اللغة، الإصدار، والاستخدام.

## تطبيق الرسم والكتابة الآن

المصدر الرسمي أصبح:

```text
apps/1-4/drawing-writing-foundations/
```

أما:

```text
1-4/
```

فهو **Compatibility Gateway فقط** للروابط القديمة وPWA السابق، ولا يحتوي مصدر التطبيق الحقيقي. بهذه الخطوة أصبح أول تطبيق فعلي في مكانه القياسي دون قطع الروابط القديمة.

## لماذا لم ننقل كل صوت الرسم إلى مكتبة مشتركة فورًا؟

لأن إعادة الاستخدام يجب أن تكون **مقاسة وليست متخيلة**. الصوت وPCM والمزامنة اليوم مملوكة لتطبيق الرسم. عندما يحتاجها تطبيق ثانٍ:

1. نحدد الجزء المشترك فقط.
2. نستخرج Runtime إلى `packages/`.
3. ننقل الأصول التي أصبحت مشتركة إلى `resources/`.
4. نحافظ على Adapter داخل التطبيق القديم إذا لزم التوافق.
5. نختبر Big TAB HD والأجهزة الحديثة قبل حذف المسار القديم.

هذا يقلل التكرار من دون المخاطرة بكسر تطبيق عامل.

## مستويات عمق التطبيقات

ليس كل تطبيق بحاجة إلى Backend وAI:

- `lite`: HTML/JS محلي، ممارسة واحدة واضحة، صفر خدمات.
- `standard`: PWA، حفظ محلي، صوت/وسائط أو أكثر من مستوى تدريب.
- `advanced`: مزامنة أو تقييم أو تسجيل وسائط أو قدرات متعددة.
- `expert`: خدمات Server، AI، حسابات أو مزامنة متعددة الأجهزة، Processing مركزي.

العمق **ليس تقييم جودة**؛ التطبيق الخفيف قد يكون الأفضل تربويًا إذا كانت المهمة بسيطة.

## Runtime Profiles

- `static-web`: تطبيق متصفح خفيف.
- `legacy-web`: دعم مقصود لأجهزة/متصفحات قديمة.
- `pwa`: تثبيت وOffline وتحديثات.
- `node-service`: خدمة Backend مستقلة.
- `hybrid-web-service`: تطبيق متصفح يعتمد على خدمة أو أكثر.

يمكن أن يبدأ التطبيق `static-web` ثم ينتقل لاحقًا دون تغيير هويته أو goal keys.

## Capability Model

بدل أن يسأل كل تطبيق: أي مكتبات أركب؟ يعلن **ماذا يحتاج**:

```json
{
  "capabilities": [
    "storage.local",
    "audio.recorded",
    "pwa.offline"
  ],
  "bundles": ["legacy-child"]
}
```

`data/capabilities.json` يصف القدرات، و`bundles/` يجمعها في وصفات شائعة. عندما يصبح لدينا Build Resolver آلي، يستطيع قراءة هذه الحقول وتجميع Dependencies/Services المطلوبة فقط.

## Bundles وليست Mega Framework

الحزمة هي وصف تركيب، مثل:

- `static-core`
- `legacy-child`
- `collaborative`
- `ai-assisted`
- `full-learning`

لا يعني اختيار Bundle أن كل كودها يحمّل في كل صفحة. الهدف لاحقًا أن تكون **Dependency Resolution Input** للبناء والنشر.

## سياسة Node.js والاعتمادات

الجذر يملك:

- `package.json`
- `pnpm-workspace.yaml`
- `.npmrc`
- lockfile واحد بعد `pnpm install`

أي تطبيق Node أو خدمة Node لا تنشئ Dependency Universe مستقلًا. تستخدم Workspace الجذر. pnpm يمنع الهدر عبر content-addressed store والربط بين Workspaces، مع `node-linker=hoisted` لتبسيط توافق الأدوات التي تتوقع `node_modules` تقليديًا.

المبدأ الصحيح ليس «نسخة واحدة بالقوة لكل Dependency»، لأن بعض المشاريع قد تحتاج إصدارات مختلفة لأسباب توافق؛ الصحيح هو **إدارة مركزية + dedupe عندما يسمح SemVer + اختلاف مقصود عند الضرورة**.

## التوافق القديم والحديث معًا

لا نجعل Big TAB HD يحدد Stack المنصة كلها. بدل ذلك:

- Platform Shell يبقى خفيفًا.
- التطبيقات التي تحتاج Legacy تعلن `runtime_profile: legacy-web`.
- التوافق القديم يعزل داخل adapters/packages محددة.
- التطبيقات الحديثة تستطيع استخدام Build حديث دون تحميل Polyfills غير لازمة للجميع.

هذا يسمح بالتقدم تقنيًا دون التضحية بمستخدم الأجهزة القديمة.

## Local-first افتراضيًا

عند عدم الحاجة إلى Server:

- البيانات تبقى محليًا.
- لا نرسل أسماء/رسومات/صوت لخدمة خارجية بلا حاجة.
- Progress Sync يضاف كCapability عند وجود سبب حقيقي.
- AI يمر لاحقًا عبر `ai.gateway` لا عبر API keys داخل المتصفح.

## استراتيجية التطوير من محادثات مستقلة

كل محادثة تطبيق تعمل داخل Boundary محدد:

```text
apps/<age>/<slug>/
```

وتقرأ العقود العامة فقط. لا تحتاج معرفة تفاصيل تطبيقات أخرى. عند الحاجة إلى شيء مشترك لا تنسخه؛ تسجل طلب استخراج Package أو Service واضح.

## Definition of Done معمارياً

أي تطبيق يصبح `live` عندما:

1. له `app.json` و`package.json` وREADME.
2. رابط الدخول يعمل مباشرة.
3. goal keys سليمة أو مبرر `modern_extension` واضح.
4. Runtime profile وDepth محددان.
5. القدرات/Bundles المعلنة صحيحة.
6. لا يعتمد على ملفات تطبيق آخر.
7. fallbacks الحرجة مختبرة.
8. `node tooling/validate-platform.js` ينجح.

## قاعدة التطور الطويل

لا نعيد بناء المنصة كلها عند ظهور تقنية جديدة. نضيف Package أو Service أو Bundle، وننقل التطبيقات إليها تدريجيًا. الهوية، الأهداف، والمسارات تبقى مستقرة؛ التنفيذ الداخلي يمكن أن يتطور باستمرار.
